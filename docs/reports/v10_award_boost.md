### 1.3 人力节省测算（核心 KPI）

```
日均工单：10000 单/天
AI 处理比例：70%（简单工单全自动） + 20%（AI 辅助人工，节省 50%） + 10%（完全人工）
加权 AI 节省率：70% × 100% + 20% × 50% + 10% × 0% = 80%

单工单平均节省：
- 简单工单（70%）：30 分钟 → 5 分钟，节省 25 分钟
- 辅助工单（20%）：30 分钟 → 15 分钟，节省 15 分钟
- 加权单工单节省：25 × 70% + 15 × 20% + 0 × 10% = 20.5 分钟/单

日均节省：
- 总节省：10000 单 × 20.5 分钟 = 205000 分钟 = 3417 小时/天
- 折算人力：3417 小时 ÷ 8 小时/天 = 427 人/天

年度人力等效：
- 427 人/天 × 365 天 = 155855 人·天/年
- 按 22 工作日/月、12 月/年：155855 ÷ 250（年人均工作日） ≈ 623 人·年
```

**结论**：
- **AI 处理 70% 简单工单后，OP 10000 工单/天的业务规模，等效节省约 427 人/天**
- **折合年度人力：约 620 人·年（按年人均 250 工作日）**
- **OP 真实团队规模按 50-100 人测算：AI 等效节省 4-8 倍团队人力**

## 2. 核心 Prompt 设计专章（结构化 Prompt 工程实践 · 不夸大原创性）

> ⚠️ **定位声明**：本节不是"自创 Prompt 范式"，而是**结构化 Prompt 工程实践**——
> 把领域知识（OP 业务）、LLM 能力边界（结构化输出）、业务规则（合规、降级）系统化编码到 Prompt 中。
> 业内常见的角色锚定 + 结构化输出不算原创，本节重点讲**为什么这样组合、解决了什么具体问题**。

### 2.1 PDA Prompt（支付诊断）— 3 层结构设计

**实际 Prompt**（`legacy/agents/payment_diagnosis/llm_provider.py:130-135`）：

```
你是 OP 跨境支付的支付诊断专家。
问题：{country} {channel} 渠道，问题类型={problem_type_hint}
证据链：
- {e.type}: {e.id} | {e.description}

请输出 JSON：{'root_causes': [...], 'recommended_actions': [...], 'confidence': 0.0-1.0}
```

**设计思路（3 层结构）**：

| 层级 | 元素 | 解决痛点 | 设计选择 |
|------|------|---------|---------|
| **L1 角色锚定** | "你是 OP 跨境支付的支付诊断专家" | LLM 默认走"通用助手"角色，输出泛泛而谈 | 强制锚定领域专家角色，约束回答粒度（不说"建议联系客服"，直接给错误码归因） |
| **L2 上下文压缩** | 问题 + 证据链（结构化字段）| 商户口语化 query 信息密度低 | 强制要求**先收集证据再回答**（risk_rule / channel_status / config_snapshot 三类），避免 LLM 编造 |
| **L3 结构化输出约束** | JSON schema + required 字段 | 自由文本输出难以下游处理（评分卡 / 派单 / 自动化）| 强约束 `confidence` 字段（0-1），下游 Orchestrator 据此判断是否触发链式 |

**思维链设计**：Prompt 中**没有**显式写"step by step"，而是让 LLM 内部推理。但通过 `evidence_chain` 字段要求 LLM **必须引用证据**——这等价于隐式思维链（每条 root_cause 必须能映射到证据）。

**迭代历史**：
- V1.0：单段 prompt + 自由文本 → LLM 经常"建议联系银行"，归因不准确
- V1.1：加证据链要求 → 输出格式稳定性显著提升（JSON schema 必填字段强制）
- V1.2：加 confidence 字段 → Orchestrator 可基于置信度触发链式（PDA→TRA）

> 注：版本迭代是**稳定性 + 可控性**的演进，非准确率绝对提升（准确率需独立标注集评测，见 §11）。

### 2.2 Orchestrator Prompt（意图识别 fallback）— 角色扮演 + 5 分类

**实际 Prompt**（`app/agents/orchestrator/orchestrator.py:61`）：

```python
LLM_INTENT_PROMPT_TEMPLATE = """你是 OceanMate AI 的意图识别助手。请判断用户问题属于以下 5 类之一：
- merchant_success: 商户选型、支付方式咨询、跨境支付基础知识
- payment_diagnosis: 支付失败、拒付、退款异常、错误码归因
- ticket_routing: 工单创建、查询、处理进度
- knowledge_evolution: 知识库查询、FAQ、案例检索
- operation_panel: 运营数据、统计、dashboard

用户问题：{query}

请严格输出 JSON：{{"intent": "<类别>", "confidence": 0.0-1.0}}"""
```

**设计思路**：

| 设计点 | 解决痛点 |
|-------|---------|
| **5 选 1 强约束** | 避免 LLM "既要又要"，明确单意图 |
| **角色锚定** | "意图识别助手" 强制 LLM 只做分类，不回答商户问题（防止路由走偏） |
| **JSON + confidence** | 同 PDA — confidence 用于 fallback 链式触发 |
| **类别词定义在 prompt** | 不依赖外部 enum 定义，零样本可用 |

### 2.3 TRA Prompt（路由）— 规则优先 + LLM 兜底

**设计**：`docs/data/ticket_routing_rules.json` 共 10 条规则（VIP/Premium/Standard × high/medium 4 层降级），**LLM 仅在规则未命中时兜底**。

**Prompt 设计思路**（简化）：
```
你是 OP 工单路由助手。根据工单信息选择最匹配的处理团队。
团队列表：财务团队-争议处理 / 风控团队 / 客户成功团队 / 技术支持团队
规则：{rules_json}
工单：{ticket_summary}
请输出 JSON：{"team": "<团队>", "sla_hours": <数字>, "reasoning": "..."}
```

**为什么不直接用 LLM？**：
- **可解释性**：规则命中 100% 可追溯（评审可读 JSON）
- **确定性**：VIP + high → 财务团队-争议处理 4h SLA，规则永远不漂移
- **LLM 兜底**：仅处理未覆盖 case（如新兴支付方式异常），LLM 给 reasoning 后人工 review

### 2.4 MSA Prompt（商户顾问）— **反问式设计** ⭐

> **本节是 OceanMate Prompt 设计中最有特色的部分**（其他都是行业标配）。

**设计思路**：商户咨询往往**信息不全**（没说明国家、客单价、行业），MSA 不强行回答，而是**主动反问采集上下文**。

```
你是 OP 商户顾问。商户画像不完整时，请先反问 1-2 个关键问题：
1. 目标市场国家（必填）
2. 客单价区间（决定是否需要分期）
3. 行业类型（B2C / B2B / 数字商品）
4. 月交易量（决定通道推荐权重）

若画像完整，请直接推荐支付方式 + 风险点。
```

**为什么用反问而非强行回答**：

| 场景 | 强行回答 | 反问采集 |
|------|---------|---------|
| 商户只说"想接支付" | LLM 答"请选择支付方式"（无价值）| LLM 反问"您主要做哪个国家？什么行业？客单价？"| 
| 商户说"想做欧洲" | LLM 答"可考虑 Visa/MC"（笼统）| LLM 反问"具体哪个国家？客单价？是否需要分期？" → 给出 NL iDEAL/DE Klarna 等具体方案 |
| 商户画像完整 | LLM 给详细推荐 | LLM 给详细推荐 |

**设计意图**：让 AI 模拟**资深商户顾问**的沟通方式（先了解背景，再给方案），而非"无脑问答机器"。

**Demo 验证**（`demo_04_nl_payment_recommend`）：商户说"NL 站 时尚 B2C 客单价 €80"，MSA **无需反问**直接推荐 iDEAL（基于 4 个完整字段）。

## 3. AI 优雅兜底机制（产品设计理念）

> **背景**：AI 客服最大的痛点不是"答错"，而是"答不出时的尴尬"——商户被一句"我不知道"打发，体验极差。
> **OceanMate 解法**：当 AI 置信度 < 0.7 或证据缺失时，**自动升级为"智能交接简报"**——AI 把已知信息整理成结构化简报，发给对应团队 lead，商户收到"已升级处理 + 预计 X 小时响应"。
>
> ⚠️ **实现状态**：当前仅 **L3 智能交接简报已实现**（Day 10 完成），L1/L2 为 V1.5 设计规划。

### 3.1 三层兜底机制（**L3 已实现 · L1/L2 V1.5 规划**）

```
┌────────────────────────────────────────────────────┐
│  L1 · AI 直接回答（置信度 ≥ 0.9）          [V1.5 规划]│
│      立即返回结构化答案（含证据链 + 推荐路径）       │
│      商户体感：8 秒拿到答案                          │
├────────────────────────────────────────────────────┤
│  L2 · AI 辅助 + 人工 review（0.7-0.9）    [V1.5 规划]│
│      AI 给答案 + 自动创建工单待 review               │
│      商户体感：拿到答案 + 升级保障                    │
├────────────────────────────────────────────────────┤
│  L3 · 智能交接简报（< 0.7 / 证据缺失）   ✅ Day 10 已实现│
│      AI 不强行答，整理"已知信息 + 待确认问题"        │
│      飞书 send_private 发给团队 lead                  │
│      商户体感："已升级，预计 X 小时响应"              │
└────────────────────────────────────────────────────┘
```

> **当前可演示能力**：仅 L3（智能交接简报），用于 PDA confidence < 0.7 或 TRA 路由未命中场景。
> **L1/L2 设计已文档化**，V1.5 实施需配套：商户端满意度反馈 + 自动工单系统 + 置信度阈值调优。

### 3.2 L3 智能交接简报（实际实现）

**触发条件**：
- PDA 诊断 `confidence < 0.7`，或
- TRA 路由规则未命中，或
- 商户 query 信息不全（如没说国家、错误码）

**简报结构**（保护内部信息 · 仅发团队 lead）：

   · 时间：周末凌晨
   · 商户等级：Premium

   · 错误码（商户未提供）
   · 受影响订单数

### 3.3 设计价值

| 维度 | 价值 |
|------|------|
| 商户体验 | 没有"我不知道"，永远给明确预期（"已升级 X 小时响应"）|
| 内部协同 | lead 收到结构化简报，不用从零看对话历史 |
| 合规安全 | 简报仅含 problem_summary + SLA + assignee，**不含交易金额/拒付率**（保护商户商业机密）|
| AI 优雅 | 不强行给低质量答案，保持 AI 系统的可信度 |

### 3.4 与"AI 客服"的本质区别

| 维度 | 传统 AI 客服 | OceanMate 优雅兜底 |
|------|------------|-------------------|
| 答不出时 | "抱歉我不理解您的问题" | "已为您升级到 NL 团队，预计 2 小时响应" |
| 工单创建 | 商户要重复描述问题 | AI 自动整理对话历史 + 关键信息 |
| 团队协同 | 商户被踢皮球 | lead 收到结构化简报，10 分钟内可回复 |
| 数据闭环 | 答完即失 | 简报沉淀到 KEA，下次同类问题 AI 命中 |

## 5. 数据安全与合规设计

> **背景**：支付行业是强监管行业，商户交易数据、拒付数据都是敏感数据。
> **原则**：**最小化数据 + 端到端可审计 + 严格权限控制**

### 5.1 数据分级

| 数据级别 | 数据类型 | 存储要求 | 访问权限 |
|---------|---------|---------|---------|
| L4 绝密 | 商户交易金额、银行卡号、拒付率 | 加密存储 + 审计日志 | 仅数据团队 + 合规审计 |
| L3 机密 | 商户 ID、订单号、错误码 | 加密传输 + 访问日志 | 运营团队 + 客服 lead |
| L2 内部 | 国家、渠道、行业类型、问题分类 | 业务库存储 | 全员可读 |
| L1 公开 | 支付方式介绍、行业知识 | 多维表公开区 | 商户可读 |

### 5.2 加密与传输

| 维度 | 设计 |
|------|------|
| 传输加密 | TLS 1.3（飞书 API + LLM API + 商户 webhook）|
| 存储加密 | L4 数据 AES-256 加密，密钥由 HashiCorp Vault 管理 |
| 脱敏规则 | 商户 ID 哈希化（SHA-256 + salt）|
| 日志审计 | 所有 LLM 调用记录到审计库（含 prompt + response + trace_id）|

### 5.3 权限控制

```
┌─────────────────────────────────────────────────┐
│  L1 公开数据：商户可读（飞书智能伙伴直接返回）      │
├─────────────────────────────────────────────────┤
│  L2 内部数据：OP 全员可读 + 商户不可见              │
├─────────────────────────────────────────────────┤
│  L3 机密数据：仅运营 lead + 客服 lead 可读          │
│       ↓ 业务需要                                │
│  L4 绝密数据：仅数据团队 + 合规审计可访问          │
│       ↓ 审计需要                                │
│  AI 调用：仅返回脱敏后的证据链（不含 L4 数据）     │
└─────────────────────────────────────────────────┘
```

### 5.4 合规框架对齐

| 合规标准 | 当前状态 | Phase 2 工作 |
|---------|---------|-------------|
| PCI DSS | 未认证 | Phase 2 启动认证（4 周准备 + 4 周审计）|
| GDPR（欧盟商户）| 部分对齐 | Phase 2 增加 right-to-be-forgotten 流程 |
| 中国《个人信息保护法》| 部分对齐 | Phase 2 增加数据出境合规审查 |
| OP 内部数据安全规范 | 待对齐 | Phase 2 与 OP 安全团队对齐 |

### 5.5 数据保留策略

| 数据类型 | 保留期 | 过期处理 |
|---------|-------|---------|
| 商户咨询日志 | 2 年 | 自动归档到冷存储 |
| 诊断结果 + 证据链 | 1 年 | 商户可申请删除 |
| LLM 调用日志 | 90 天 | 脱敏后保留做评测 |
| 审计日志 | 5 年 | 不可删除（合规要求）|

### 5.6 已知 gap（坦诚声明）

- 当前 Demo 阶段数据安全是**设计层规划**，未做实际 PCI DSS 认证
- 密钥管理当前用 `.env` 文件，Phase 2 必须迁移到 Vault
- 数据脱敏当前是字段级，Phase 2 需做行级（按商户 ID 隔离）

## 9. 人工反馈闭环（KEA 负反馈机制）

> **背景**：当前 KEA 只沉淀"已解决案例"，没有"AI 答错被纠正"的负反馈机制。
> **本节设计**：让负反馈也进入数据飞轮，让 AI 越用越聪明。

### 9.1 反馈类型

| 类型 | 触发 | 反馈源 |
|------|------|--------|
| 👍 正反馈 | 商户确认"解决了" | 商户确认动作 / 飞书表情 |
| 👎 负反馈 | 商户反驳"不对"/ lead 修正答案 | 商户对话 / 人工 review |
| 🔄 修正反馈 | lead 修正 AI 答案后回写 | 人工修正 |

### 9.2 反馈处理流程

```
商户对话 → AI 回答 → 收集反馈
                            ↓
            ┌──────────────┴──────────────┐
            ↓                             ↓
       正反馈                       负反馈 / 修正
            ↓                             ↓
    KEA 入库（置信度+0.1）          人工 review
                                           ↓
                                  修正后答案入库
                                  （置信度 -0.2 初始）
                                           ↓
                                  下次同类问题检索时
                                  优先返回修正版本
```

### 9.3 实现要点

| 维度 | 设计 |
|------|------|
| 反馈采集 | 飞书智能伙伴内置 👍/👎 按钮 + 商户"解决了"指令 |
| 反馈存储 | 飞书多维表 `feedback` 表（含 original_answer / corrected_answer / feedback_type）|
| 入库策略 | 修正反馈自动创建 KEA 候选，但 `confidence` 初始为 0.5（低于 0.9 自动入库阈值），强制人工审核 |
| 权重调整 | 多次负反馈的错误答案 → 降低向量库召回权重 |
| 看板 | OPA 增加"负反馈率"指标，>5% 自动告警 |

### 9.4 与"正向飞轮"的差异

| 维度 | 正向飞轮 | 负向飞轮 |
|------|---------|---------|
| 数据源 | 已解决案例 | AI 答错的修正案例 |
| 置信度起点 | 0.7-0.9（基于 LLM 自信度）| 0.5（强制人工审核）|
| 价值 | 扩展知识库 | **修正错误 · 比正向更稀缺** |
| 落地难度 | 易（自动） | 难（需 lead 主动修正）|

### 9.5 V2.0 路线图

- Phase 2（3 个月）：负反馈 UI + 自动入库
- Phase 3（6 个月）：负反馈权重学习（基于反馈频次自动调权重）

## 10. LLM 成本测算（千商户 × 万问题/天）

> **背景**：大规模用 LLM，成本是关键商业化指标。

### 10.1 调用频率假设

| 调用类型 | 单商户/天 | 1000 商户/天 | 10000 商户/天 |
|---------|----------|------------|--------------|
| 商户咨询 MSA | 3 次 | 3000 | 30000 |
| 支付诊断 PDA | 1 次 | 1000 | 10000 |
| 工单路由 TRA | 0.5 次 | 500 | 5000 |
| 知识检索 KEA | 2 次 | 2000 | 20000 |
| 意图识别（Orchestrator）| 6.5 次 | 6500 | 65000 |
| **合计 LLM 调用** | **13 次** | **13000 次/天** | **130000 次/天** |
| **Embedding** | 13 次 | 13000 | 130000 |
| **Rerank** | 3 次 | 3000 | 30000 |

### 10.2 单价假设（Qwen DashScope 公开定价）

| 调用类型 | 单价 | 来源 |
|---------|------|------|
| qwen-turbo（LLM）| 0.003 元/千 token | DashScope 公开定价 |
| 平均 prompt 长度 | 500 token | 实测（含证据链）|
| 平均 response 长度 | 300 token | 实测 |
| 单次 LLM 成本 | (500+300)/1000 × 0.003 = 0.0024 元 | |
| text-embedding-v3 | 0.0007 元/千 token | DashScope |
| 单次 Embedding 成本 | 100 token × 0.0007/1000 ≈ 0.00007 元 | |
| qwen3-rerank | 0.005 元/千次 | DashScope |

### 10.3 月成本测算

```
日成本（10000 商户）：
- LLM：130000 × 0.0024 = 312 元
- Embedding：130000 × 0.00007 = 9.1 元
- Rerank：30000 × 0.005 = 150 元
- 日合计：471 元

月成本（30 天）：
- 471 × 30 = 14130 元 ≈ 1.4 万元/月

年成本：
- 1.4 × 12 = 16.9 万元/年
```

### 10.4 成本优化策略

| 策略 | 预期节省 | 实施成本 |
|------|---------|---------|
| **语义缓存**（重复 query 命中率 40%）| -40% LLM 成本 | 2 周开发 |
| **小模型 fallback**（简单问题用 qwen-turbo-lite）| -30% LLM 成本 | 1 周开发 |
| **批量 Embedding**（异步批量调用）| -50% Embedding 成本 | 3 天 |
| **Rerank 跳过**（top-1 分数 > 0.9 时跳过）| -40% Rerank 成本 | 1 周 |
| **合计优化后** | **-60% 综合成本** | 4 周 |

**优化后月成本：约 0.6 万元/月（7 万元/年）**

### 10.5 ROI 对比

```
原成本：1.4 万/月
优化后：0.6 万/月
年度优化后成本：约 7 万元/年
对比 §1.5 ROI 测算（1600%）：极度划算
```

## 11. 评测体系（准确率/召回/满意度）

> **背景**：AI 系统需要持续评测才能优化，不能"上线就跑"。

### 11.1 评测维度

| 维度 | 指标 | 计算方式 | 目标值 |
|------|------|---------|-------|
| **诊断准确率** | AI 诊断与人工诊断一致 | 抽样 100 工单，请专家评分 | ≥ 85% |
| **RAG 召回率** | Top-5 包含正确答案 | 200 条标注 query 集 | ≥ 90% |
| **RAG 精确率** | Top-5 中正确比例 | 同上 | ≥ 60% |
| **意图分类准确率** | Orchestrator 分类正确 | 500 条标注 query | ≥ 92% |
| **商户满意度** | 👍/👎 + 文字反馈 | 飞书按钮统计 | ≥ 80% |
| **响应时延** | p50 / p99 延迟 | Prometheus 监控 | p99 ≤ 5 秒 |
| **降级率** | LLM 降级 Mock 的比例 | trace 日志统计 | ≤ 5% |

### 11.2 评测数据集

| 数据集 | 规模 | 来源 | 更新频率 |
|-------|------|------|---------|
| PDA 标注集 | 200 条 | OP 真实历史工单（脱敏）| 季度 |
| MSA 标注集 | 150 条 | 行业标准咨询场景 | 半年度 |
| 意图分类集 | 500 条 | 人工标注 | 月度 |
| 满意度反馈 | 实时 | 飞书按钮 | 持续 |

### 11.3 评测流程

```
每日：自动评测意图分类准确率（用昨日反馈）
每周：人工抽检 20 条 AI 回答评分
每月：完整评测集回归 + 报告
每季：评测集扩充 + 模型升级评测
```

### 11.4 A/B 测试框架

- 新 Prompt / 新模型上线前，对照组（旧）+ 实验组（新）各跑 1000 工单
- 主指标：商户满意度 + 诊断准确率
- 显著性检验：p < 0.05 才全量上线

## 12. 冷启动问题（新商户无历史数据）

> **背景**：新商户接入 OceanMate 时，**没有历史工单、没有画像、KEA 知识库里也没有这个商户的案例**——AI 怎么工作？

### 12.1 三阶段冷启动策略

```
┌────────────────────────────────────────────────────┐
│  阶段 1（0-30 天）：通用知识库兜底                   │
│  · 用 OP 全量 117 错误码 + 16 支付方式做基线         │
│  · 不区分商户，给通用推荐                            │
│  · 商户满意度预期：60-70%                            │
├────────────────────────────────────────────────────┤
│  阶段 2（30-90 天）：画像积累                        │
│  · 收集商户前 30 天咨询 + 工单                       │
│  · MSA 自动补全画像（国家/客单价/行业）              │
│  · 商户满意度预期：70-80%                            │
├────────────────────────────────────────────────────┤
│  阶段 3（90+ 天）：个性化推荐                        │
│  · 基于历史工单训练商户专属向量                       │
│  · KEA 沉淀商户特定 FAQ                              │
│  · 商户满意度预期：80-90%                            │
└────────────────────────────────────────────────────┘
```

### 12.2 冷启动期商户标识

| 标识 | 含义 | AI 行为 |
|------|------|---------|

| `is_cold_start=true` | 0-50 工单 | 同上 |

### 12.3 冷启动期 UX 提示

## 13. 异常场景处理（商户生气/AI 答不出/系统挂）

> **背景**：真实业务中 AI 必然遇到异常场景，必须有兜底机制。

### 13.1 异常场景分类

| 场景 | 触发条件 | 兜底机制 |
|------|---------|---------|
| **商户情绪激动** | 文字含"投诉""退订""骗子"等关键词 | 转人工 + 优先级提升到 high + 简报抄送 lead |
| **AI 答不出** | LLM confidence < 0.3 | 触发 §3 智能交接简报 L3 |
| **LLM API 挂** | DashScope 返回 5xx | 自动降级 MockLLMProvider（已实现）|
| **向量库挂** | Chroma 连接失败 | 自动降级纯 BM25（PoC 简化）|
| **飞书 API 挂** | send_private 失败 | 队列重试 3 次 + 失败写日志告警 |
| **数据缺失** | 商户咨询无错误码 | MSA 反问采集 + 推荐路径 |
| **重复咨询** | 同商户 5 分钟内 3 次同问题 | 自动合并 + 转人工 |
| **超长对话** | 对话 > 50 轮 | 自动压缩上下文 + 触发交接简报 |

### 13.2 异常检测机制

```
┌──────────────────────────────────────────┐
│  L1 关键词检测（实时，零延迟）              │
│  · 商户生气关键词：投诉/退订/骗子/投诉      │
│  · 触发：自动转人工 + 优先级提升            │
├──────────────────────────────────────────┤
│  L2 行为检测（事后分析）                    │
│  · 重复咨询 ≥ 3 次 → 合并工单              │
│  · 对话长度 > 50 轮 → 触发交接              │
├──────────────────────────────────────────┤
│  L3 系统健康检测（实时监控）                │
│  · LLM API p99 > 10 秒 → 告警              │
│  · 降级率 > 5% → 告警                     │
│  · 错误码 5xx > 1% → 告警                  │
└──────────────────────────────────────────┘
```

### 13.3 商户情绪管理 SOP

1. 检测到情绪关键词 → 立即回复"已为您升级，X 团队 Y 同事将尽快联系您"
2. 创建 high 优先级工单 + 智能交接简报
3. 抄送 lead + 客服 supervisor
4. 30 分钟内人工必须响应（强制 SLA）

### 13.4 系统挂的兜底

- **LLM 挂**：自动降级 Mock（已知 pattern），trace 标记 degraded=True（已实现）
- **向量库挂**：自动降级 BM25（待补）
- **飞书挂**：队列重试 + 失败写日志 + 告警 lead（待补）
- **整体挂**：商户智能伙伴回复"系统维护中，请稍后重试"+ 紧急联系入口

### 13.5 已知 gap（坦诚声明）

- 商户情绪检测当前是关键词级，未做情感分析 LLM
- 重复咨询检测未实现（依赖人工）
- LLM 降级到 Mock 时，返回的是固定答案，非真实个性化
