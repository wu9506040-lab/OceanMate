# OceanMate 业务架构与演进路线（PoC → 生产）

> 这份文档记录：系统**当前真实做到什么**、**为什么这样设计**、**要上生产还差什么、怎么补**。
> 目的不是堆架构词，而是把"一个跨境支付商户成功助手要成立，必须解决哪些真问题"讲清楚。

---

## 0. 一句话产品定位

商户在飞书群/私聊提出支付问题 → 智能客服能追问补全信息、基于知识库作答 → 答不了自动转人工工单 → **学习人工的解法回灌知识库** → 下次同类问题自己解决。目标：AI 自助解决率持续提升、人工介入率下降。

核心是**数据飞轮**：知识不是运营手写的，是"商户问题 + 人工解法"持续沉淀出来的。

---

## 1. 数据飞轮：四个环节，当前状态

```
        ┌──────────────────────────────────────────────┐
        │                                                │
   [采集] 商户提问 → [作答] 检索知识库 → [反馈] 👍/ → [进化] 案例转FAQ → 回灌[作答]
        │                                                │
        └──────────────────────────────────────────────┘
```

| 环节 | 作用 | 当前实现 | 状态 |
|---|---|---|---|
| 采集 | 意图路由、追问补全参数 | Orchestrator 两级路由；PDA 缺参反问（scene/code_required 分类） | ✅ 有 |
| 作答 | 检索知识 + 生成 | 混合检索（向量 + BM25 + RRF + rerank）；**读取侧已接通 faq_vec** | ✅ 本次接通 |
| 反馈 | 商户/运营对答案打分 | `POST /api/feedback` → 写 review_decisions（👎=rejected 回复审池） | ✅ 本次新增 |
| 进化 | 已解决案例→FAQ→入库 | 关单自动沉淀 → 三段置信度审核 → faq_vec | ✅ 有 |

**读取侧接通是本次关键**：此前"存得进取不出"（案例入 faq_vec 但作答主链路从不查它，飞轮空转）。现在 `route_pda` 出结论后按"同国 + 同错误码/问题类型 + 有真实解法"确定性匹配历史解法，命中优先展示"上次实际怎么解决的"。

> 诚实边界：匹配判据是**确定性的错误码/问题类型相等**，不是语义相似度——这是为了"绝不用错知识误导商户"（宁可少命中也不误命中）。语义级匹配是下一步。

## 2. 人工交接（Human-in-the-loop）

### 2.1 触发路径（现有）
- 商户显式"转人工/派单/投诉" → 路由 TRA
- PDA 低置信(<0.45) → 先追问补数据，补不齐再升级
- problem_type ∈ {拒付/支付失败/Webhook回调失败} → 高价值场景直接建工单

### 2.2 已修的设计缺陷
- **误触发**：原 `_URGENT_HINTS` 含"支持/客服/联系"等日常词，商户问"Visa 支持3DS吗"会被误判建 high 工单。已收窄为显式升级诉求词（转人工/派单/投诉/紧急…）。
- **链式矛盾**：`chain_config` 的 PDA→TRA 与 `webhook._maybe_chain_to_tra` 是两套，后者更激进。产品决策是"bot 答得了不打扰人工"，两处需统一（见 §5 待办）。

### 2.3 目标架构（生产需要，PoC 未做）
- **工单仅人工可见**：现在简报走 `send_private`（1v1 私信 lead），方向对；缺**结构化接管入口**——应为飞书**交互卡片**带"接管/已解决"按钮 + callback，而非现在的"打字咒语 + 手动 sync-bit"。
- **交接审计**：handoffs 表已建但零写入。生产应每次人工介入落库（谁接管、耗时、最终解法），既是 SLA 依据也是飞轮的"人工解法"数据源。

## 3. 隐私：单群方案是错的，双轨制才对

当前演示把所有商户放一个群 —— **真实场景不可接受**（商户 A 能看到商户 B 的拒付问题）。

正确设计（PoC 未做，架构预留够）：
1. **一问一私聊**：bot↔商户 1v1（`send_private` 已有雏形），问题不进公共群。
2. **转人工才建群**：需要团队协作时，为该工单建"处理群"（lead + 相关方），完结即归档。
3. **多维表格按行权限**：工单表用 bitable 的行级权限，lead 只看到分派给自己的工单。
4. **PII 脱敏**：订单号/商户 ID 进日志和知识库前做脱敏（数据清洗层预留）。

## 4. 知识库怎么切、怎么治理

### 4.1 切分（现有真实实现）
`SmartChunker` 按内容自动选策略：短文本整条 / QA 对切 / Markdown 分节 / 超长滑窗（1024/64）兜底。两级清洗器（默认 / 激进）。**但规模假设 ≤200 条**，是 PoC 边界。

### 4.2 治理（生产缺口）
"知识库自更新"目前**只有新增、没有更新与淘汰**：
- 无版本：FAQ 入库即定稿，政策变了不会自动失效
- 无命中统计：哪条 FAQ 真被用过、用过几次、用完商户是否满意——无埋点
- 无去重合并：两个相似案例各自 approve → 两条近似 FAQ（embedding_meta 只按 case_id 去重，不按语义）

生产需要：**FAQ 版本化 + 命中率埋点 + 语义去重 + 低质降权回炉**。

## 6. 与"数据中台"叙事对齐的诚实说明

本项目**当前**在数据层面的真实能力：
- 多采集通道（消息/图片/群/bitable 读写，真 httpx）
- 混合检索入库管道（清洗→分块→embed→store，幂等）
- 一条案例→FAQ→检索的知识飞轮闭环（写入 + **本次接通读取**）
- 运营指标聚合（`opa_metrics`：错误码/渠道/置信度/审核通过率/周趋势，REST + 周报文件）

本项目**尚未**具备的"中台"能力（不写进简历，此处仅立为 roadmap）：多源 schema 归一化、AI 字段真实落库打标、实时看板服务、CDC/水位线增量同步、数据质量监控、血缘。

> 判断标准：**简历和 README 只写第 1 段（能当场演示/被代码验证的）**；第 2 段作为 roadmap 说明"我知道边界在哪、下一步怎么走"——这本身是加分的业务理解，而非要冒充的既成功能。
